# Reactive MP 重构与完善计划

状态：2026-11-12 已开始实施；当前包结构、测试、文档与验证状态见 [架构文档](architecture.md) 和 [验证记录](verification.md)。以下保留原始阶段目标。以当前工作区为基线；保留已有修改与暂存状态，不重置或批量清理。

## 目标与设计约束

Reactive MP 是原生微信小程序的运行时增强库。继续使用原生 JS、WXML、WXSS、Page、Component 及平台配置，不引入 Vue 方言、模板编译器或生产中间代码。

保留同一 setup 的一次配置收集和多次实例运行：注册时执行但不建立响应式订阅，实例创建时建立状态、依赖、闭包和生命周期。只要平台所需的任何注册信息仍需收集，这条阶段边界就存在；不以缩减动态声明能力来声称消除了复杂度。

原生静态配置与 setup 动态声明均为正式用法，可以混用。普通业务无需判断阶段；高级适配可读取阶段信息。收集过程不是 JS 源码解析。运行时只能管理经过本库 API 的副作用，不承诺隔离任意用户代码。

examples 是包的开发、联调、问题复现及真实平台验证宿主，不是最终阶段才制作的演示成品。它们从 monorepo 迁移开始就参与开发。

## 一、简化现有实现与约束

### 1. 梳理行为契约

建立 API 清单，记录每项能力在配置收集、实例创建、挂载、销毁阶段的行为、返回值及资源归属。以当前导出和实际消费者为依据，标注稳定、未完成、内部能力；同步审查上一轮修复，不将现有测试通过等同于设计已经正确。

明确原生与动态声明的合并规则，覆盖 data、methods、properties、options、behaviors、relations、observers、lifetimes、pageLifetimes、export 和页面事件。区分覆盖、合并和处理函数组合，避免依靠对象展开顺序形成隐含契约。

### 2. 收敛运行时结构

- 配置收集与实例运行共享 API 协议，内部由各自的上下文处理器执行，不要求业务分支。
- 配置结果归注册定义所有；响应式状态、订阅、闭包和清理函数归实例所有。
- 当前上下文的进入、恢复、异常清理由统一作用域边界处理，支持嵌套，不依靠散落的 reactive/inactive 调用维持正确性。
- 页面与组件在注册入口确定适配方式；共享逻辑不反复推导宿主身份。
- 区分注册方式和页面角色，完成 Component 注册页面的现有设计，避免多个布尔值产生无效组合。
- 生命周期、事件、配置键、合并策略等可枚举领域采用集中声明表，供注册、分发、类型和文档核对使用；不把所有问题做成通用插件系统。

### 3. 放宽过度预防性检查

逐项处理现有断言、类型识别、保护标记与调用次数限制：

| 情形 | 处理原则 |
| --- | --- |
| 页面/组件已有明确入口、上下文提供了对应能力 | 不再重复推导身份；类型提示和入口负责表达 |
| 能自然合并的重复声明 | 按明确规则合并，不仅为限制调用方式而报错 |
| 原生平台已有合法配置 | 保留透传，不用狭窄白名单拦截扩展 |
| 缺少真实实例、调用发生在销毁后 | 就近给出具体错误或明确的安全行为，不能静默丢失工作 |
| 只读写入、循环更新、资源泄漏等实际不变量 | 保留必要保护，错误说明真实原因 |
| 高级反射及阶段查询 | 保留明确入口，不出现在普通使用流程中 |

验收：常用页面和组件不使用阶段判断即可完成动态声明和组合 Hook；限制均能对应具体运行后果，不再仅为约束开发者写法而存在。

## 二、完善未完成能力

按使用闭环推进，每项完成时同步更新 API 文档、自动化测试和验证宿主中的对应场景。

### A. 响应式内核

- Signal、computed、watch、watchEffect：调度顺序、旧值、动态依赖、批量更新、循环和异常行为。
- effect scope：嵌套、父子释放、暂停/恢复、停止后待执行任务及重复销毁。
- reactive/ref/mutable/carrier：深层读写、增删替换、数组、相同值写入、只读语义、身份复用及嵌套订阅清理。
- 验证无追踪收集阶段与正常追踪阶段一致的取值语义，以及回调和订阅的阶段隔离。

### B. 小程序运行时

- App/Page/Component 全链路；审查 App 全局响应式数据与生命周期。
- data 初始同步、setData 路径更新与回调、属性更新、视图写入时机及反馈循环。
- 原生与 Hook 生命周期组合、事件参数和返回值；分享等需要返回值的页面回调不能只靠事件总线广播。
- properties 默认值、真实值、后续更新及观察器组合。
- provide/inject：父子、跨层、默认值、Symbol、实例销毁、祖先变化及绑定时机。
- relations、defineExpose、组件页面、原生 Behavior 的混合使用。
- Hook 的返回值、this、原生实例访问、定时任务及清理语义。

### C. Store 与公共接口

- 合并当前两份未完成 Store 实现，形成单一入口。
- 明确 store 定义、首次实例化、共享范围、state/getters/actions、订阅和释放；防止配置收集阶段提前初始化全局副作用。
- 完成所有公开能力的类型声明与导出检查，减少全局类型污染，避免用宽泛类型掩盖核心契约。
- 空模块、占位符和未完成 API 明确标注；views/wxapi 是否需要正式能力依据实际场景决定，不为填空而添加接口。

验收：公开 API 没有无说明的空实现；核心场景有可执行回归及平台验证记录。Node mock 验证和微信实机/开发者工具验证分别记录，不互相替代。

## 三、monorepo 与开发宿主

### 建议目录与包职责

```text
packages/
  shared/          # 通用工具、事件总线、调度基础；无 wx 依赖
  reactivity/      # 核心包一：Signal、对象响应式、依赖与 effect scope
  store/           # 基于 reactivity 的可选状态管理工具包
  runtime/         # 核心包二：收集、实例、平台适配、生命周期和小程序 Hook
  reactive-mp/     # 面向用户的统一入口，保留 reactive-mp 的使用定位
examples/
  playground/     # 常驻开发宿主：功能实验、状态观察、核心能力联调
  integration/    # 平台验证宿主：原生混用、多实例、多页面、组件关系等
  scenarios/      # 完整业务宿主：共享状态、请求、列表等组合场景
apps/
  docs/           # 文档站渲染及导航；正文来源统一管理
docs/             # 指南、API、原理、贡献说明及决策记录
tests/            # 跨包契约测试、验证宿主辅助及共用测试设施
```

包名作用域发布前再确定，避免提前要求 npm 组织权限。

依赖方向：shared → reactivity → store；runtime 依赖 shared/reactivity；统一入口组合 runtime/reactivity/store。这里箭头表示基础层供上层使用。reactivity/store 不依赖小程序运行时，shared 不通过 barrel 反向依赖上层。生命周期 Hook 属于 runtime，不为每个目录单独发包。

工作区统一管理依赖、测试和文档命令；根包设为 private。每包声明明确 exports、类型入口、依赖与发布文件范围。先建立可用包边界，不同时引入不必要的任务编排或版本发布系统。

### examples 的日常开发机制

1. 每个宿主是可由微信开发者工具直接打开的原生小程序工程，自己的 app.json、project.config.json、页面、组件、WXML/WXSS 均在工程内。
2. 宿主消费当前工作区包，不依赖已发布 npm 版本、不手动复制源代码、不保留第二份实现。
3. 先用最小宿主验证开发者工具对 workspace 依赖的实际读取方式。若需将依赖同步到小程序工程可读取目录，使用确定性的工具并可 watch；只处理包解析、搬运或平台必需格式，不转换模板或 setup 语义。
4. 联调目录、生成依赖和测试截图不作为源代码提交；文档说明从干净 checkout 一条命令准备宿主的流程。
5. 宿主页面展示可观察的预期和实际结果，提供重置与重复进入/退出操作，用于验证实例隔离、时序及清理，不只展示“按钮能点”。
6. 修复问题时优先在对应宿主加入最小复现，再加适合自动化的契约测试；稳定后保留为回归场景。
7. playground 服务日常探索；integration 保持确定场景和验收步骤；scenarios 验证能力组合是否自然，避免全部测试只验证孤立 API。
8. 尽可能建立开发者工具自动化；环境不具备时保留明确的手工步骤和真实验证记录，不宣称已完成平台验证。

验收：改动工作区包后，宿主能直接验证改动；干净 checkout 可准备并打开宿主；没有借用历史发布产物而产生的假通过。

## 四、全站文档机制

### 信息结构

- 入门：定位、安装、工作区开发、首个原生页面/组件。
- 指南：响应式、组合 Hook、生命周期、props、通信、Store、静态与动态混用。
- API：按包组织，说明参数、返回值、阶段行为、资源归属和原生映射。
- 开发验证：各宿主用途、场景入口、命令、调试与平台回归。
- 进阶原理：配置收集、实例建立、上下文恢复、依赖追踪和视图同步。
- 维护：包依赖、贡献约定、设计决策、兼容性与变更记录。

普通教程不要求读者先学习两阶段原理；副作用如何放置直接在用法中说明。需要深入时链接进阶说明，不隐藏实际限制，也不反复暴露内部状态机。

### 单一来源与检查

- README 只承担入口和快速开始，包 README 承担包边界与链接，不重复维护整份教程。
- 用现有 docs 作为文档来源，建立完整导航和静态文档站；优先 Markdown 驱动方案，工具选型在验证包格式和宿主链路后确定。
- API 清单与实际 exports 做一致性检查；签名优先从类型声明生成/核对，语义说明由人工维护。
- 文档代码优先引用开发宿主或可执行测试片段；避免维护“看起来正确”的另一份示例。
- 检查内部链接、导航、代码引用、API 覆盖和文档构建。文档站能本地预览并在 CI 构建，公开托管不属于自动授权范围。
- 每项 API 或行为变更同步文档、类型、场景和回归；未验证能力明确标记状态。

验收：从首页能找到全部公开能力；代码片段可追溯到真实源文件；陈旧示意 API 被替换；构建和链接检查可自动运行。

## 五、实施顺序与阶段交付

| 阶段 | 工作 | 交付与验收 |
| --- | --- | --- |
| P0 基线与契约 | 审查当前修改、能力盘点、合并规则、检查分类；跑现有回归 | 能力/缺口矩阵、测试基线、待验证平台行为清单 |
| P1 工作区和最小宿主 | 建 workspace、迁移现有实现与演示、拆出 shared/reactivity/runtime/统一入口，建立包消费链；Store 暂不冒充完成 | 原有回归继续通过；playground 可打开并使用工作区核心包；文档站骨架同步建立 |
| P2 简化与内核完善 | 作用域边界、集中声明表、放宽重复约束、完善响应式对象及调度、独立 Store | 包级测试及 integration 场景逐项通过；变更契约同步文档 |
| P3 平台能力闭环 | 页面/组件/App、组件页面、原生混用、观察器、事件返回值、关系与实例清理 | integration 验证记录，scenarios 验证真实组合；完成公共类型与导出 |
| P4 文档与交付收口 | 补全指南/API/原理、源码引用、链接校验、CI、包产物和兼容检查 | 文档全站可构建；干净安装可运行验证；发布候选包可由独立宿主消费 |

文档和宿主从 P1 开始随开发更新，P4 是完整性收口，不是到最后才补。

## 六、完成标准

- 保留并完善全套动态收集能力；静态配置可选，不强迫使用者拆分同一份组合式逻辑。
- 常规使用不需要阶段判断，必要的原生限制有准确说明。
- 主要检查从“防止开发者这样写”收敛为“保证具体运行不变量”。
- 两个核心包职责清楚，依赖单向，基础包不依赖 wx。
- 每项公开能力均有类型、文档、自动化或真实平台验证依据。
- examples 真正成为日常开发及回归设施，持续消费当前工作区实现。
- 根命令能运行测试、类型检查、文档检查、文档构建及宿主准备；无密钥、个人 AppID 依赖或隐含本地文件。
- 发布与公开部署另行执行，不把本地构建通过当作已发布或已实机验证。
