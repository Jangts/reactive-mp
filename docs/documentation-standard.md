# 文档规范

本规范适用于 Reactive MP 仓库的 README、指南、API 参考、架构说明、开发宿主说明、维护手册及由这些来源生成的文档站。公共包、原生小程序宿主和开发工具遵循同一内容原则。

## 正式文档

正式文档解释当前确定的产品定位、接口合同、设计和操作方式。读者无需了解项目讨论、实施阶段或旧方案，即可据此接入与使用。

- 说明解决的问题、前提、输入输出、默认值、策略、职责、错误和真实限制，示例与公开导出一致。
- 按成品组织已确定的合同，不使用“本轮完成”“即将支持”“尚待接入”等实施进度表述。合同与实现有差异时，在独立问题或计划中跟踪并修复；不能在指南中承诺已可使用，也不以差异记录代替正式用法。
- 不叙述对话、授权、迁移经过、成果数量或前后版本比较。设计依据写成自足的技术理由，避免引用“用户要求”“之前讨论”等背景。
- 准确说明适用环境、组件框架、渲染后端、基础库和运行时边界。真实限制是使用合同，应保留；尚未完成的验证不是产品特性，归验证记录。
- 普通教程说明如何放置实例副作用、如何读取和更新状态，不要求读者先理解阶段判断。配置收集、实例创建和追踪机制在进阶原理中解释；不能为隐藏阶段而隐瞒直接执行用户代码的边界。
- 保留原生 JS、WXML、WXSS、JSON 与平台 API 的各自职责。明确哪些能力由运行时接入、哪些直接使用原生；“可透传”不等于“完整动态支持”或“平台验证通过”。
- 不把未决定的选择写成产品能力。正式参考不设置“待确认”“开放问题”“后续计划”等项目管理段落。
- SDK 使用页面不介绍文档站如何生成、托管、审计或发布；这些说明服务站点维护者，放在维护入口。

## 过程资料

计划、能力差距盘点、设计讨论、调查、变更记录、问题复现和验收记录各自独立，标题与索引清楚标明用途。它们不构成第二套正式接口文档。

- [开发计划](development-plan.md)记录目标、范围、依赖、工作批次和待办。
- [平台能力清单](platform-coverage.md)记录原生能力对照、缺口及后续验收，不因有导出或 Record/any 类型而判定支持。
- [验证记录](verification.md)记录实际执行、版本、场景、结果、证据与未验证边界。
- 一次性工具输出、截图、打包检查回执和复现报告保存到忽略提交的 artifacts；长期维护结论整理进相应维护文档。不得写入凭据或隐私数据。
- 调整目录或导航时保留有效链接、必要证据和明确约束，不删除失败记录以制造通过结果。

使用指南和 API 导航与维护规范、计划、验证记录分别组织。正式文档可以链接独立的维护入口，但不在正文复述实施时间线和验收数量。

## 内容归属与单一来源

| 来源 | 责任 |
| --- | --- |
| 根 README | 项目定位、首次接入及使用／开发入口；不复制全部指南 |
| 包 README | 包的独立用途、运行前提、真实安装与最小用法、继续使用和交付链接 |
| packages/<公开包>/docs | 该包独立的概览、接入、指南、API 与文档导航；正文唯一来源 |
| packages/<公开包>/docs/api.md | 仅由该包真实 exports 与对应类型声明生成的 API 签名参考 |
| docs/api.md | 工作区全量 API，包含维护者需要的内部支撑包 |
| packages/reactive-mp/docs/setup-runtime.md | 配置收集、实例、上下文、追踪及视图同步原理 |
| docs/architecture.md | 包边界、源码组织、工具与维护操作的入口 |
| apps/docs | 导航、渲染、预览与文档站交付，不维护第二份正文 |
| examples | 包的开发、复现、联调和平台验证宿主，也是代码示例的来源 |
| docs 计划与记录 | 与正式合同分开的实施信息和验证证据 |

生成内容修改其来源并重新生成。文档片段优先使用 `<<< examples/...` 引用真实宿主；需要独立片段时说明接入文件、上下文和预期，不能用未定义变量冒充可运行代码。不要直接修补 dist、vendor 或生成的 API 页面。

examples 的实验场景不自动成为推荐用法。被教程引用的片段应已具备稳定合同和对应检查；宿主应消费当前工作区包，而非另一份复制实现或旧发布版本。

## 原生能力与类型的写法

- 参数和返回值对照微信原生语义，保留异步结果、合法空值、事件参数、this、属性及回调顺序。平台专属字段注明适用环境，不能把其他平台同名接口混入微信参考。
- 静态配置、动态声明、模块化类型和平台验证分别陈述。对框架接管的部分说明合并／覆盖规则，不让读者依赖源码展开顺序猜测优先级。
- 配置收集与实例运行的公共行为使用同一份正式合同；仅在真实差异影响使用时说明。不能宣称配置收集是沙箱、源码解析或任意副作用隔离。
- 基础包的无平台能力、runtime 的平台依赖和统一入口的聚合关系保持一致。独立包示例不能依赖未声明的上层包、wx 全局或工作区私有路径。
- 引用官方规范优先使用官方文档、类型和源码，记录平台能力盘点的基线。资料无法核实时标记证据边界，不据印象补造支持项。

## 公开包的随包文档与文档站

每个 release.type=public 的包必须提供自己的 docs 目录。包通过 reactiveMp.docs 声明 docs/site.json，由它登记标题、定位和分组导航；至少包含概览、快速上手、使用指南和 API，并随 npm 包交付。内部领域随所属公开包组织，共用内部包保留在工作区维护入口。

公开包默认拥有独立站点，也可在 docs/site.json 中用 site 指定承载文档的公开包名。Reactivity 的 site 为 reactive-mp：主站直接读取 packages/reactivity/docs 的指南和 API，以 reactivity- 前缀建立路由、导航和搜索，不生成独立 Reactivity 站点。该声明不改变 npm 发布身份、版本或随包文档归属。

Kit 内的 Wechat、Images Preloader 由 packages/kit/docs 提供指南和 API，不再维护独立包或站点；Store 的独立包、随包文档与站点保留，Kit 文档说明其转发入口并链接完整 Store 指南。

站点品牌和页头版本来自站点所属包；被承载包在其导航组标明自己的版本。导航、搜索索引与 API 只包含该站点承载的包。静态输出包含所需样式、脚本、品牌素材和源码页面，移动到独立目录或部署子路径后仍能使用。独立站点的使用导航不链接仓库维护页面，不依赖相邻站点的输出目录。

各站可以共用构建、模板和交互实现，不复制另一份正文。包 README 保留首次使用并链接包内 docs；docs 与站点声明随 npm 白名单交付。主包文档也放在自己的 docs 中；docs 根目录承担工作区入口和维护资料。

## 公开包的使用入口与发布检查

公开包 README 服务首次接触该包的使用者。已有有效结构只补明确缺口，不为统一字数、模板或排版而重写；已有语言顺序与切换入口保持不变。

发布前检查：

1. 定位与前提：任务、运行环境、平台要求、运行依赖和 peer 依赖与实际包一致。
2. 首次使用：真实安装命令、完整公开 import、最小代码、接线文件／位置、执行方式与预期结果。小程序包说明原生工具的消费方式，基础包说明独立使用方式。
3. 继续使用：提供常见任务、参数、结果读取、默认值、错误和资源寿命的必要说明；链接不能替代最小有效引导。
4. 链接与交付：核对发布白名单和实际 tarball。包 README 的相对链接必须随包交付，或使用明确公开且可访问的文档地址；不能依赖仓库外的 docs 或本机路径。
5. 搜索元数据：description 和 keywords 描述实际任务及环境，以使用者会搜索的词为主；不凑数量、不堆泛词、不宣传未实现能力。

工作区使用方式与 registry 安装方式分别说明。尚无实际发布证据时，不将包名存在写成公共 registry 已可安装。维护者的 monorepo 安装、工具构建和审计操作不作为消费者的接入前提。

发布时核对最终包体中的 README、类型、exports 和元数据。发布授权独立于文档或代码修改；发布成功后核对公共 registry 的版本、标签、完整性、README、元数据及实际可安装性。仓库文件检查和本地打包不代替公共可用性验证。

## 同步、审校与验证

接口、默认值、配置、合并策略和行为发生变化时，同步责任文档、index.d.ts、实际示例、API 来源和文档站。兼容性决策与缺口归维护资料，已确定的用法归正式参考。

审校按语义判断，不批量删除“历史”“状态”“恢复”“计划”等词；这些词也可能描述合法的产品或平台概念。检查读者、事实、合同、代码来源、链接和重复参考是否一致。

根据改动选择最小有效检查：

- 文档链接、导航或引用变化：`npm run docs:check`。
- 导航渲染、源码引用或页面生成机制变化：增加 `npm run docs:build`。
- API 来源变化：`npm run docs:api`，再核对生成差异与相关类型／行为。
- 示例变化：按具体疑问选择类型、离线或平台验证；记录所用包与宿主来源。

纯文档修改不自动触发整套测试、开发者工具启动、真实外部调用、压测或发布。生成检查不证明语义和可用性完整；实际执行与未执行项写入维护记录或交付说明，不写进正式教程正文。

## 双语与组件参考

所有公开站点的使用文档必须提供完整的中文和英文版本。中文保存在所属包 docs，英文保存在 docs/en，随同一个 npm 包交付。标题、侧栏、搜索、API、上下篇与页内目录随语言切换；缺译必须在构建前报错。签名和默认值引用同一真实定义，不能以中文回退或只有英文标题冒充英文文档。

组件站按实际原生 wrappers 建立逐组件文档，每页说明适用任务、完整 JS/JSON/WXML、属性类型/默认值、事件详情、插槽、实例方法与边界。复杂行为另有模型校验、Hooks 和样式指南。可选 wrapper 的基础外观与应用视觉职责必须清楚，不把文档站样式捆绑给消费项目。
