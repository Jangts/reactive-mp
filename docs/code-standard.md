# 代码规范

本规范规定 Reactive MP 的书写方式、代码职责和文件落位，适用于公共包、原生开发宿主及长期维护工具。[代码检查与验收标准](code-review-standard.md)规定如何审查及举证，[文档规范](documentation-standard.md)规定面向使用者和维护者的文档，两者不替代本规范。

## 适用范围

| 对象 | 要求 |
| --- | --- |
| packages 中的实现与 index.d.ts | 遵守完整书写、职责、依赖和文件规则 |
| examples 中长期保留的页面、组件和组合逻辑 | 保持原生工程结构、明确状态与生命周期，便于开发和复现 |
| scripts、apps/docs 中的正式工具 | 遵守可读性、文件职责、关键函数说明及文件／进程边界 |
| 测试、临时探针和一次性片段 | 以场景清晰、断言有效为主，不强制逐函数 JSDoc 或额外拆文件 |
| vendor、dist、生成的 API 参考 | 修改生成来源，不手改产物，不以产物格式反向改写人读的源码 |

规则用于减少阅读和维护成本，不以固定行数、函数数量、类数量、文件数量作为质量判断。既有代码调整须有明确范围；新增规范不自动授权全库格式化、改名或重排。

## 一、书写规范

### 格式与表达

| 编号 | 规则 |
| --- | --- |
| W01 | 使用 UTF-8、LF、文件末尾换行、2 空格缩进，不留行尾空格。JavaScript／TypeScript 使用分号、单引号和多行尾逗号；JSON 使用双引号。格式化工具由根配置统一，不逐包维护冲突规则。 |
| W02 | 每条语句独立成行，条件、循环和异常处理使用清楚的代码块。不把赋值、计数、调用和返回堆成一条表达式，不以逗号运算符、连续逻辑短路或嵌套三元表达式隐藏流程。 |
| W03 | 简单纯表达式可以直接返回；存在副作用、多个分支或顺序约束时展开书写。短箭头函数用于局部映射／选择，具名函数用于需要独立理解和定位的处理单元。 |
| W04 | const 优先，变量确需重赋值才使用 let，不使用 var。相关状态按职责声明，不把无关变量合在同一个声明中。重复读取与解构以语义稳定为前提，不丢失 this、getter 或实例身份。 |
| W05 | 每行以约 80 字符为格式化参考，交给统一工具处理合理例外，不为达到宽度拆坏标识符、URL 或语义单元。导入、对象和参数较长时按项分行。 |

格式规则是源码要求，不代表现有文件已经格式化。只有实际存在并使用对应配置、检查过适用范围，才能声明格式检查通过。引入工具配置时限于本次授权范围；测试与临时文件不为形式统一增加机械工作。

### 命名与术语

| 编号 | 规则 |
| --- | --- |
| W06 | 变量、函数和方法使用 camelCase；类、构造类型、interface／type 使用 PascalCase。布尔值用 is/has/can/should 等表达真实问题，避免无语义 flag。集合用复数，数量和时长带清楚单位，如 intervalMs。 |
| W07 | 函数名表达动作或结果，如 collectOptions、bindSignals、disposeScope；避免含糊的 handleData、process、doThing。允许小范围惯用名，禁止为了缩短而使用无法理解的缩写。 |
| W08 | 区分注册定义、实例、页面角色、追踪与资源作用域。相同概念保持同名，不把 options、context、scope、instance 相互替代；不把状态容器和它的值混称。 |
| W09 | 保留原生 Page、Component、setData、pageLifetimes 及字段名称。平台字段不因内部命名偏好改写，适配层负责映射。内部常量使用能表达职责的名称；不因一个值是 const 就全部大写。 |

### 注释、类型与导入

| 编号 | 规则 |
| --- | --- |
| W10 | 模块顶部说明职责、所属层和主要入口。公开函数说明参数、返回、错误、阶段差异和资源归属；非显然逻辑解释为什么。采用中文说明及原始技术标识符，不逐行翻译代码，不保留过期调试结论和大段注释掉的旧实现。 |
| W11 | 实现沿用原始 ESM JavaScript，公开合同在模块化 index.d.ts 中维护；语言迁移单独决定。类型保留泛型、只读、联合类型和异步返回；未知数据先用 unknown，不能用 any、类型断言或全局声明掩盖契约缺口。 |
| W12 | 外部／工作区依赖与包内相对导入分组，类型导入使用 import type。JavaScript 相对导入写明 .js 扩展名；跨包走已声明的公开入口。包内按明确模块导入，避免通过自身聚合 index 绕回产生循环。仅供 JSDoc 引用的类型不引入无用运行时依赖。 |
| W13 | 不导出未完成占位、无职责别名或同实现的平行入口。具名导出优先；已有兼容 default／别名按既定合同处理，不为风格统一擅自破坏消费者，也不无限增加历史兼容层。 |

### 控制流与错误

| 编号 | 规则 |
| --- | --- |
| W14 | 参数缺省用默认参数或 ?? 表达；只有把全部假值视为缺省符合合同才使用 \|\|。显式保留 0、false、空字符串、null 和 undefined 的不同含义。 |
| W15 | 提前返回用于缩短不适用分支，不跨过必要清理。上下文恢复、锁和资源释放使用对应的结构化边界；不要依靠每个返回点手工恢复。 |
| W16 | 错误指出实际阶段、对象与原因，必要时保留 cause。没有职责的 catch-and-rethrow 删除；不吞错、打印后假装成功，或以可选链静默丢失必须完成的工作。可选能力才允许明确的空行为。 |
| W17 | 调试日志不进入热路径和正常使用输出。日志说明事件，不倾倒整个上下文、实例、数据或秘密值。诊断失败不改变业务结果。 |

可读性示例：先说明时序和副作用，而不是把步骤压缩成一条表达式。

```js
// 以下仅示意书写方式；不是新增公开 API。
function emitAndSchedule(task, schedule) {
  task();
  schedule();
}
```

## 二、代码组织规范

### 职责与抽象

| 编号 | 规则 |
| --- | --- |
| O01 | 每个模块拥有能说明的输入、输出、前提、副作用和错误；入口负责装配，编排负责阶段与顺序，处理器负责明确工作，基础设施负责通用机制。不把所有逻辑塞入注册函数，也不拆成只增加跳转的细碎转发。 |
| O02 | 函数完成一个连贯任务，类拥有一组真实状态和不变量。函数、对象和类按职责选择，不为统一范式重写；私有成员用于封装状态，不用于遮掩本可参数化的重复变体。 |
| O03 | 相似功能复用共同实现，使用参数或登记表达差异。不复制文件改几个名称派生新实现；只有生命周期、平台约束或合同确有差异时分别适配，并保留共享处理路径。 |
| O04 | 生命周期、事件、配置键、合并策略等稳定可枚举领域使用集中声明表，实际驱动注册、分发和相关校验。算法、时序、单条件判断继续使用直白流程，不为套清单而制造通用规则引擎。 |
| O05 | 工具按职责和真实复用范围归属。仅一个模块使用的辅助逻辑先留在该模块或同目录，不提前塞进 shared；跨模块也不意味着必须单独发包。避免任意扩张 utils、helpers、common、etc 等杂物容器。 |

### 注册、实例与资源

| 编号 | 规则 |
| --- | --- |
| O06 | 保留同一 setup 的配置收集与实例运行。共享声明协议，由内部阶段处理器承担差异；不要求普通业务为绕过库而拆分静态／动态逻辑，也不通过删除动态功能降低内部复杂度。 |
| O07 | 稳定配置归注册定义；可变状态、闭包和订阅归实例；共享业务状态归 Store；单次异步状态归本次任务。注册对象不能保存某个实例的活动信息，内部函数和实例引用不能进入视图 data。 |
| O08 | 上下文的进入、恢复、嵌套和异常收尾由统一作用域边界负责；不让处理器成对调用 activate/deactivate 维持隐含状态。清理有明确所有者、释放点和幂等语义，一项失败仍处理其余资源。 |
| O09 | 仅在真实边界校验真实不变量。注册入口已明确页面／组件时，不在公共流程重复猜测身份；合法重复声明依合同合并。只读、循环更新、已销毁对象等检查必须对应实际后果，不能依赖窄白名单拦截合法平台扩展。 |
| O10 | 保留原生调用者、参数和返回值。返回值 Hook、异步结果和广播通知分别处理，不能为了接口外形统一破坏平台语义。构造或 import 不启动与实际调用无关的监听、定时器或平台注册。 |

### 包与宿主边界

| 包或目录 | 所有职责 | 不应承担 |
| --- | --- | --- |
| packages/shared | 通用事件、调度、类型与基础工具 | wx、页面身份、Store 或 runtime 规则 |
| packages/reactivity | Signal、依赖追踪、对象响应式、effect scope | 原生组件注册和视图渲染适配 |
| packages/store | 共享状态、惰性实例及其资源寿命 | 页面实例管理与原生平台初始化 |
| packages/runtime | 配置收集、实例、平台适配、生命周期与 Hook | 工具端文件操作或业务应用规则 |
| packages/reactive-mp | 用户统一导出 | 第二套状态、注册或执行机制 |
| examples | 场景组合、复现和实际平台验证 | 核心包的复制实现或私有替代版本 |
| scripts / apps/docs | 工作区工具与文档站 | 被小程序入口导入的生产依赖 |

依赖由 package.json 和 exports 表达，按上述职责保持单向。不能通过相对路径、隐式 workspace 解析或工具 loader 绕过边界。公开 package 不能要求消费者具备仓库私有文件或上层包。

示例中真正复用的业务组合放在该宿主内的组合模块；能证明属于库的能力才回归公共包。不要为把示例做短而把演示业务塞进核心。

## 三、文件组织规范

### 根目录与固定入口

```text
packages/             公共包和统一入口
  <package>/
    package.json      依赖、导出和发布文件范围
    README.md         独立接入与文档入口
    index.d.ts        公开模块类型
    src/
      index.js        包实现入口／导出
      <domain>/       确有规模和职责边界的领域模块
examples/             原生开发与验证宿主
  <host>/
    app.js / app.json / app.wxss
    project.config.json
    pages/            页面及其同名原生配套文件
    components/       组件及其同名原生配套文件
    vendor/           工具生成，不手改、不提交
apps/docs/            文档站生成、预览和导航
scripts/              长期维护的正式开发工具
tests/                自动化回归、类型和跨包契约
docs/                 正式文档及独立维护资料
artifacts/            忽略提交的临时证据和输出
lib/index.js          既定旧入口兼容桥，不扩展为第二套实现
```

目录示意表达职责，不要求为没有文件的层级创建空目录。

| 编号 | 规则 |
| --- | --- |
| F01 | 根目录只放工作区配置、固定入口和一级职责目录，不散放领域实现、临时脚本或发布包体。新增文件先归现有责任目录，不随意新建平行体系。 |
| F02 | 同领域按职责集中，目录层数由真实规模决定。不把多类责任平铺在一个文件夹，也不为每个小函数创建目录。涉及多个包的内容在共同工具或测试边界组织，不放到某个包后让其他包反向借用。 |
| F03 | 目录使用 kebab-case。函数／工具模块使用有意义的 kebab-case 文件名，主要导出类的文件使用 PascalCase；类型使用 PascalCase 标识符。现有文件名不因新增规则批量改名；文件系统大小写与 import 完全一致。 |
| F04 | 已有 index.js、index.d.ts 等固定入口保持稳定。只在真实公共边界设置聚合入口，不为每层目录都建 barrel；新文件用具体名称，避免 main2、new、final、temp 等无法表达职责的名称。 |
| F05 | 原生页面和组件的 js/json/wxml/wxss 同目录、同基名。页面组合、局部 Hook 和样式放在所属宿主；跨页面共享内容再提升到宿主相应目录，不跨宿主相对导入。 |
| F06 | 测试沿用根 tests：按 reactivity、runtime、workspace 等被测责任组织；类型用例归 tests/types，复用测试设施归 tests/helpers（确有需要时）。使用 *.test.mjs／明确的类型用例，不把测试设施发进生产包。 |
| F07 | 长期维护工具归 scripts，文档站专用工具归 apps/docs。正式工具不得依赖 /tmp 或某台电脑的固定私有路径；临时探针和回执归 artifacts 或任务临时目录，不伪装成可维护入口。 |
| F08 | 包只发布明确白名单中的实现、类型、README 和必要资源；检查实际 tarball，排除宿主、测试、凭据、个人项目配置及临时产物。相对文档链接须在交付中有效。 |
| F09 | vendor、dist、生成 API 与包体由工具产生。修改源稿后生成；清理只处理工具明确拥有的产物，保留用户内容，不用清目录掩盖同步错误。 |
| F10 | 移动、拆分和删除文件时同步 imports、exports、类型、生成工具、测试、源码引用及文档链接；保留既定兼容合同，不留下同职责旧副本。文件迁移与语义调整尽量分开核验。 |

## 四、变更与检查

修改时先确定实际职责和消费者，再判断需要局部编辑、抽取公共实现还是调整包边界。结构变动应能解释减少了什么重复、明确了谁的责任，不能只把行数从一个文件搬到另一个文件。

- 书写／排版变化：检查目标 diff 和适用格式配置，不改行为。
- 实现／组织变化：核对共同路径与受影响消费者，按疑问执行必要回归。
- 文件／包边界变化：核对解析、公开导出、类型和独立消费，不能仅证明 workspace 中可运行。
- 文档／生成来源变化：按[文档规范](documentation-standard.md)选择链接和生成一致性检查。

不为规范整理顺手全库重排、换语言、改公开 API 或安装工具链。范围内的例外说明真实理由；检查状态使用[审查标准](code-review-standard.md)的通过、不通过、未验证、不适用，不把“写了规范”当作全库已符合规范。
